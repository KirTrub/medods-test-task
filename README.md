# Task Service

HTTP API на Go для управления задачами медицинского персонала. Поддерживает ручное создание задач и автоматическую генерацию периодических задач по расписанию с настраиваемыми дедлайнами.

## Требования

- Docker и Docker Compose

## Быстрый запуск

```bash
docker compose up --build
```

После запуска API доступен на `http://localhost:8080`.

> **Примечание:** Если база данных уже запускалась ранее со старой схемой, пересоздайте volume:
> ```bash
> docker compose down -v && docker compose up --build
> ```

## Архитектура

Проект построен по принципам чистой архитектуры:

```
cmd/api/          — точка входа, сборка зависимостей
internal/
  domain/task/    — доменные модели (Task, Schedule, Status, Parity)
  usecase/        — бизнес-логика (task, schedule)
  repository/     — работа с базой данных (PostgreSQL)
  transport/http/ — HTTP-обработчики, роутер, Swagger
  scheduler/      — фоновый воркер генерации задач
migrations/       — SQL-миграции
```

## API

Полная документация доступна через Swagger UI:

- **Swagger UI:** `http://localhost:8080/swagger/`
- **OpenAPI JSON:** `http://localhost:8080/swagger/openapi.json`

### Задачи (`/api/v1/tasks`)

| Метод  | Путь              | Описание                |
|--------|-------------------|-------------------------|
| GET    | /api/v1/tasks     | Список всех задач       |
| POST   | /api/v1/tasks     | Создать задачу вручную  |
| GET    | /api/v1/tasks/:id | Получить задачу по ID   |
| PUT    | /api/v1/tasks/:id | Обновить задачу         |
| DELETE | /api/v1/tasks/:id | Удалить задачу          |

Поля задачи:

| Поле          | Тип       | Описание                                                     |
|---------------|-----------|--------------------------------------------------------------|
| `id`          | int64     | Идентификатор                                                |
| `title`       | string    | Название (обязательное)                                      |
| `description` | string    | Описание                                                     |
| `status`      | string    | `new`, `in_progress`, `done`, `overdue`                      |
| `schedule_id` | int64?    | Заполняется автоматически при генерации из расписания        |
| `deadline_at` | datetime? | Дедлайн. Устанавливается планировщиком из `deadline_days`    |
| `created_at`  | datetime  |                                                              |
| `updated_at`  | datetime  |                                                              |

> Статус `overdue` устанавливается **автоматически** планировщиком в полночь, если `deadline_at < now` и задача ещё не завершена. Вручную выставить `overdue` нельзя.

### Расписания (`/api/v1/schedules`)

| Метод  | Путь                   | Описание                       |
|--------|------------------------|--------------------------------|
| GET    | /api/v1/schedules      | Список всех расписаний         |
| POST   | /api/v1/schedules      | Создать расписание             |
| GET    | /api/v1/schedules/:id  | Получить расписание по ID      |
| PUT    | /api/v1/schedules/:id  | Обновить расписание            |
| DELETE | /api/v1/schedules/:id  | Удалить расписание             |

При удалении расписания уже сгенерированные задачи сохраняются (их `schedule_id` обнуляется).

## Типы периодичности

### `daily` — каждые N дней

Задача создаётся каждые `every_n_days` дней, начиная с даты создания расписания.

```json
{
  "title": "Обзвон пациентов",
  "type": "daily",
  "every_n_days": 1,
  "deadline_days": 3
}
```

### `monthly` — в конкретный день месяца

Задача создаётся в указанный день каждого месяца (от 1 до 30).

```json
{
  "title": "Формирование отчётности",
  "type": "monthly",
  "day_of_month": 15
}
```

### `specific_dates` — конкретные даты

Задача создаётся только в указанные даты.

```json
{
  "title": "Квартальный аудит",
  "type": "specific_dates",
  "dates": ["2026-03-31", "2026-06-30", "2026-09-30", "2026-12-31"]
}
```

### `parity` — чётные/нечётные дни

Задача создаётся каждый чётный или нечётный день месяца.

```json
{
  "title": "Инвентаризация",
  "type": "parity",
  "parity": "even"
}
```

## Дедлайны

Поле `deadline_days` в расписании определяет, через сколько дней истекает сгенерированная задача:

- `deadline_days: 0` (или не указано) — задача создаётся без дедлайна
- `deadline_days: 3` — у каждой созданной задачи `deadline_at = дата создания + 3 дня`

Раз в сутки (в полночь UTC) планировщик переводит задачи в статус `overdue`, если их `deadline_at` прошёл, а статус не `done`.

## Планировщик

Фоновый воркер запускается вместе с сервисом и работает следующим образом:

1. При старте немедленно выполняет прогон — помечает просроченные задачи и генерирует задачи на сегодня.
2. Далее ждёт наступления следующей полуночи (UTC) и повторяет прогон.

Повторное создание задачи для одного расписания в рамках одного дня предотвращается уникальным индексом `(schedule_id, date_trunc('day', created_at))`.

## Принятые решения

**Отдельная сущность `Schedule` вместо поля в `Task`** — расписание является шаблоном и порождает множество инстансов задач. Это позволяет редактировать/удалять расписание независимо от уже созданных задач.

**`deadline_days` на уровне расписания, а не задачи** — дедлайн — это свойство шаблона: «сколько времени есть на выполнение этого типа задачи». Конкретное значение `deadline_at` вычисляется при генерации.

**`StatusOverdue` недоступен через API** — переход в `overdue` является системным событием и не должен управляться вручную. `Status.Valid()` намеренно исключает этот статус из допустимых для ввода значений.
